### 游玩与操作

- 右上点击 **开始第 1 波**。正常清波后准备 **20 秒**，可点击提前开始下一波。第六波结束只结算一次，没有第七波。
- **Space / 暂停按钮**控制全局暂停；**R / 重开按钮**随时回到干净的新局准备，包括暂停中、胜利后和失败后。
- **G** 伸展，**B** 远处种芽，**C** 在所选已有菌结培育，**O** 切换攻击器官/胃囊，**L** 连接已有菌结；**T** 改向、**M** 移植、**Y** 取消未出发的移植准备。费用仍经过原系统真实付款与运输。
- **P** 仍只暂停/继续所选建设任务，**X** 取消；**F/J** 选择组织并修复，**K** 仍只暂停/继续修复，Backspace 取消修复。全局暂停时允许选择、观察和 G/B/L/T/M 预览；确认、取消、任务改序、供养和付费操作均等待恢复后重新提交，没有隐藏的暂停指令队列。
- 首次放目标、尸体回运、营养回流、成长解锁、完成分化和断路分别触发一次引导；可“知道了”或关闭/重新开启引导。没有增加无实际效果的音量或反馈设置。

### 批次身份与生命周期

- `start_batch()` 返回唯一批次身份，`start_wave()` 保留旧入口；`get_planned_count()` 在开始前提供合法计划预览，在已接受批次中读取冻结计划。主 HUD 显示实际计划总数。
- `get_batch_snapshot()` 分开提供计划、已生成、活跃、已击败、外部移除及未生成数量；始终满足「计划＝已生成＋未生成」「已生成＝活跃＋已击败＋外部移除」。外部删除活体不算击败，也不生成尸体。
- 每个已生成成员有唯一 `spawn_id`，关联 `batch_id`；计时预约另带代次与预约身份。成员入树前已登记身份和最终出生位置，同步回调停止、重置或删除对象不能多生成同组成员。
- 全部计划实际生成且活跃归零才发一次 `batch_finished`；旧 `wave_finished` 还要求全部确实击败，避免把外部清理当成玩家胜利。完成后可明确开始新批次，不会自动接下一批。
- `stop_spawning()` 取消后续生成，保留已在场敌人，并继续准确结算其死亡或移除；停止的批次不再发完成/胜利。停止后需要 `reset()` 才能重新开始。
- `reset()` 退役本生成器自己的活体和监听，清空统计，保留配置与不复用的身份序列，不自动启动。母核死亡、R重开和退出会关闭旧计时；旧计时、死亡或离树回调不能污染新的批次。其他来源敌人和已经生成的尸体不由重置误删。

## 第八阶段第四小轮：付费攻击分化

累计真实回收达到 **160**、菌落进入成熟期后，选中一个已长成的普通攻击器官，右侧「攻击器官分化」面板可选择**破甲**或**散射**。普通器官可以保留；同一器官只能完成一次方向分化，完成后不能退回普通或再次换型。新培育器官也使用同一个资格检查和面板入口。

### 付款、时间与停火

- 一次完整分化消耗 **8 营养材料**，至少需要 **5 秒有效时间**：每份已抵达材料支持一个 **0.625 秒**工作步，开工时才变为不可退款的消费。缺粮、断路或暂停时不推进；通道暂时拥堵不阻止使用已经收到的材料。
- 材料由母核付费，通过真实营养包和原有网络送到宿主。分化缓存与器官弹药分别记账，不能用库存弹药冒充材料。
- 从开始直到完成（包括等待和暂停）停止射击，也停止为该器官购买新的战斗弹药；开始前已付款的合法在途弹药仍照常到货。
- 完成时在**原武器对象**上一次性应用独立配置副本，保留原器官、宿主、网络连接、弹药和合法在途供养，不重新执行初始化，也不赠送启动库存。恢复射击等待完整的新冷却；已经飞行的弹丸继续使用原攻击参数。
- 普通每轮1、破甲每轮2、散射整轮1；破甲忽略护甲，散射沿原60°扇形最多攻击三个不同目标。本轮没有新敌人批次，也未把旧场景显式普通参数改成8.6的新战斗演示配置。

### 暂停、取消与继续

开始即锁定方向。暂停保留工作位与进度，保持停火。取消释放全局工作位，退还尚可退的缓存和在途材料，保留方向、已消费材料及部分工作步的有效时间，恢复原普通攻击并重新等待完整普通冷却。继续只能沿原方向，分配一个新的单调任务身份，再次停火，补足余下费用与时间；反复取消/继续不会补弹、复制武器或减少总费用。

面板分别显示未解锁、另一任务忙碌、缺粮、材料在途、断路、暂停和完成等原因。「规则」可展开完整取消/退款约定；P/X 仍操作原建设任务，不会暗中改为控制分化。进入建设放置或修复选线时暂时隐藏分化面板，只影响显示，不暂停后端任务。

### 冻结接口与结算

- `DifferentiationSystem`：`get_availability()`、`start_differentiation()`、`continue_differentiation()`、`pause_task()`、`resume_task()`、`cancel_task()`；`get_task_snapshot()` / `get_organ_snapshot()` 查询任务身份、方向、状态、材料和有效时间。`receive_nutrition(task_id, shipment_id, amount)` 按唯一货件收取材料；终态 `take_unspent_nutrition(task_id)` 只能领取一次可退款缓存。
- `AttackOrgan` 与状态系统共享一份分化记录，`get_attack_type()` 从实际关联武器读取行为，`has_completed_differentiation()` 保留一次完成锁。活动分化不能被通用工作启用调用意外开火。
- `DifferentiationSupplySystem` 保存每份材料的原付款来源、任务和货件身份，以 FIFO 批次核销实际消费；退款仍走原来源的普通余额入口，不增加累计回收。`DifferentiationSystem.get_resource_snapshot()` 的累计材料消费按器官去重，不按取消/继续次数重复统计。
- 正式分化只由 `ConstructionSupplyScheduler.register_differentiation_supply()` 驱动，自动独立派送关闭。活动任务登记独立轮换组，终态注销；建设调度器重置后仍活跃的分化重新认领。新付款保留修复预算及其他活跃武器的两轮真实费用储备，库存与已付款在途共同覆盖，不重复扣减。
- 所有材料包使用同一个 `NetworkTrafficSystem`，保留排队、断路等待和改道。可退款的已到货缓存不确认主脉通行；材料开始工作、变为不可逆消费时，才确认原货件实际走过的边。重入、取消、宿主移除和重开不会重复确认或退款。
- R 重开、母核死亡和退出先关闭旧任务准入，再结算各原付款账本。场景重建得到全新任务与记录；仅在同场景调用系统 `reset()` 不会洗掉器官已锁方向或已完成分化。

## 第八阶段第三小轮：选敌协作

多个攻击器官现在通过同一个 `CombatTargetingSystem` 查询和准备在途伤害，减少对已被足够攻击覆盖的敌人继续投入火力。

### 选敌优先级

先筛选地面射程内、仍存活且生命需求尚未被承诺覆盖的目标，再依次比较：

1. 是否正在攻击母核：必须是活跃敌人、母核有效且存活、位于接触距离，并且原攻击计时器确实正在运行。
2. 距母核的地面距离，更近者优先。
3. 距当前器官的地面距离，更近者优先。
4. 敌人的稳定实例身份，消除同距离目标的随机次序。

敌人通过 `is_attacking_core()` 与 `get_core_distance_squared()` 提供只读状态；查询不会启动计时器或造成伤害。
没有有效母核引用的隔离夹具使用无穷大的母核距离，继续按器官距离和身份稳定排序。
散射以最高优先级的主要目标确定方向，再从原完整扇形内选其他尚未覆盖的不同目标，仍只按整轮收费一次。
所有候选均已覆盖时等待，不发射、不扣费。

### 在途伤害与两段提交

`prepare_commitment(target, request, owner)` 为每颗弹丸分配唯一身份，准备成功后立即影响其他器官的选择。
攻击请求只保存发射时的原始伤害和伤害类型；`get_incoming_damage()` 将这些请求逐个交给敌人的纯估伤接口，
按**目标当前护甲**计算预计有效伤害，破甲仍忽略护甲。`get_remaining_health()` 返回当前生命减去这些预计伤害后的非负需求，
不会提前修改生命、母核余额、器官库存或尸体产出。

武器先准备本轮全部承诺，再实例化和校验弹丸。准备回调中即使另一器官同步射击，也已经能看到这些承诺；
本轮复核时仅忽略自己的身份，防止把自己刚准备的伤害当成外来火力而拒绝整轮。
任一目标、弹丸、配置或代次失效时，清理本轮全部草稿和承诺，保留其他器官的记录，不产生射击扣费。
`commit_batch()` 对已绑定的整批承诺统一校验和提交，随后在无公开回调的区间内完成原有本地库存扣费；
整轮提交事件继续记录实际费用，营养统计不依赖伤害预留。

### 生命周期与正式接线

- 准备阶段由发射武器负责，成功提交后归对应弹丸管理；停止或移除原武器不会撤销已经飞行的合法攻击。
- 弹丸命中、取消、超时或离树，敌人死亡或离树，均清理对应承诺；`release_commitment()` 首次成功后重复调用返回 `false`。
  命中期间保留承诺直至实际受伤结算，防止血量/死亡回调重入时看到尚未扣血但已撤销预留的窗口。
- `reset()` 取消旧弹丸和记录、推进代次并允许新工作；`stop()` 清理后停止接收新承诺。
  旧身份和延迟清理不能影响新代次，也不能在失去记录后变成无记录的攻击。

配置字段依次为 `damage`、`fire_interval`、`attack_range`、`nutrition_cost`、`max_targets`、

### 伤害接口与单次结算

伤害请求只包含 `raw_damage: int` 和 `damage_type: int` 两个必要标量；原始伤害必须大于零，
伤害类型必须是枚举中的值。缺字段、错误类型、零或负伤害均无效，不会被最低伤害规则变成攻击。
敌人的 `armor` 默认为 0，负护甲赋值被拒绝并保留原值。

- `BasicEnemy.estimate_damage(request)` 无副作用，普通/散射返回 `max(1, raw_damage - armor)`，
  破甲返回原始伤害；无效请求返回 0。估算不依赖敌人是否存活，也不按剩余血量截断。
- `BasicEnemy.apply_damage(request)` 返回实际损失血量；无效请求、已死亡或待删除敌人返回 0。
  正式发射只在弹丸命中时调用它；重复死亡结算只有一次通知和一具尸体。
- `SporeProjectile.launch_request(enemy, request)` 校验并复制发射时的伤害标量，命中前不扣血；
  后续修改配置或请求不改变旧弹丸。弹丸先标记已结算再扣血，防止死亡回调同步重入导致重复命中。
  目标死亡、释放或离树后弹丸消散，破甲只忽略护甲，不穿透多个敌人。
- 旧 `take_damage(amount)`、`launch(enemy, damage)` 保留，按普通伤害规则适配。

### 候选经过与业务确认

`CargoPassageTracker` 先记录包实际完整走完的非零菌丝段，随后由业务结算确认。
申请通行、获准进入、释放凭证、地面接近、等待及半途取消均不等于有效通过。
每份货物在每条边最多计一次；反向重走、改道和运输重试不增加相同货物的份数。
一包尸体占 2 单位通行容量，仍只算 1 份货物；包内营养数量也不作通过量乘数。

| 业务 | 稳定货物身份 | 确认位置 |
| --- | --- | --- |
| 普通战斗供养 | 原付款运输号，含供养系统身份 | 攻击器官实际接受库存后 |
| 生长供养 | 原付款批次运输号 | 原 FIFO 来源批次核销为实际延伸或菌结投入后 |
| 培育供养 | 原付款批次运输号 | 结构投入，或成熟提交后的 `startup_transferred` |
| 修复供养 | 原付款批次运输号 | 原账本将该批次计为不可退的修复消耗后 |
| 尸体回收 | 原尸体 ID 或 `carcass_batch_id` | 原胃囊实际接受该尸体后 |
| 绿色回流 | 原 `product_id` | 原母核确认收件，并完成源产物结算后 |

建设及修复的可退款缓存只保留候选，培育 `startup_reserved` 同样不确认。
取消未用批次会丢弃候选；启动器官草稿回滚不会提前确认四点启动库存。
原消费批次先全部完成 FIFO 核销，再发布主脉确认，避免升级通知同步重入时看到半提交账目。
尸体掉落重试及绿色产物回流重试保留原业务身份，运输尝试号只用于原运输结算。

确认封存该货物的候选集合，之后的迟到运输不能为已收件货物添加新边。
已完整经过的边后来暂时断开，不抹去该次真实历史；已删除的边不会被历史强引用保活。
跟踪器和主脉系统均按来源、代际及货物/边身份去重，快照不暴露可修改的账本。

## 第七阶段第三小轮：双尖端与独立成熟

正式 G/B/L/C 入口统一交给建设协调器。每个同时运行的请求使用由**原生长、供养、连接和培育脚本实例**

| 对象 | 数量规则 |
| --- | --- |
| 等待与延伸中的 G/B/L 外部目标 | 合计最多 3，暂停目标也在内 |
| 初生延伸尖端 | 最多 1，消费或损伤不会降低已达到的阶段 |
| 累计真实回收到达 60 后的尖端 | 最多 2，解锁不重启原任务；第三个目标等空位 |
| 暂停中的延伸任务 | 保留尖端名额，不能靠暂停创建更多尖端 |
| 已接通并交接到真实培育任务的 B | 移到独立成熟列表，不占外部目标或尖端名额 |
| C 就地培育 | 不占外部目标或尖端，仍由原菌结唯一槽位决定能否创建/继续 |

释放尖端有明确的提交边界：原生长真正完成、终点已登记、原生长供养已结算，原培育系统已在该终点
接受对应的芽与任务。此后保留同一 `construction_id`，原执行实例继续持有成熟账目；真正成熟仍需
**8 点结构、4 点启动库存、至少 3 秒有效培育**，不会因为显示“已接通”提前完成。
成熟任务可独立暂停、继续和取消，空闲尖端可以接手新目标；取消一个目标不清理另一个目标的缓存或运输。

### 统一供养与生命周期

统一供养调度器按目标顺序轮换，每轮每个目标最多成功派送一份原营养包；一个目标的生长与培育属于同组。
暂停、失联、无需求或已结束的供养不会挡住其他目标。先保留母核的修复预算，再保留原战斗储备，
只用剩余可花余额建设。轮换起点会推进，低余额下不会总让第一个实例抢走新收入。
受管理的供养实例关闭独立自动派送，普通 `try_dispatch()` 也被归属锁拒绝；仅所属调度器可以触发原账本。
已有在途照常只结算一次，交通容量与 FIFO 不因资金调度改变。

请求身份由 `construction_id + worker_id + 内部任务号` 共同定位，不能把不同实例都从 1 开始的任务号混用。
全部活动任务、成熟列表和资源快照均可查询；结构投入、缓存、在途及启动预留各自独立。
启动库存转入器官后只在器官库存里计算，不再把转移记录加一遍。空闲或终态实例可暂留用于原芽续建与历史核对，
但不因此继续占用尖端；回收实例前保存永久结构投入。同场景清理保留这些已投入统计，新场景重新计数。

母核死亡或 R 重开先停止统一派送并使旧回调失效，各实例通过原账本取消、退款和清理，之后才释放实例、
清理队列与原有修复/交通系统。暂停延伸不会丢掉它的占位，释放延伸占位也不会提前销毁成熟或在途仍需要的对象。

### 真实营养修复

- 每 **1 营养最多恢复 10 生命**，速度最多 **每秒 10 生命**，不会超过上限。最后不足 10 生命仍收 1，
  报价向上取整：从 0 修到 35 需要 4，从 34 修到 35 也需要 1。
- 修复任务固定原付款母核、目标边和一个作业端。优先选起点；若起点无法沿有效网络获得母核营养，
  则选终点。寻路始终排除正在修复的边，包括恢复通行后的包改道；不允许穿过断段资助另一端。
- 两端都不可供养时可以保留一个等待任务，预留和扣款均为 0。首次获得可达端后固定作业点；此后该点失联就等待，
  不把已经付款的包改送另一端。需要换端时由玩家取消后重新请求。
- 真实黄色营养包抵达作业端后才进入缓存；开始恢复生命时才消费整数营养并生成最多 10 生命的已付款额度。
  修复包与战斗、生长、培育、尸体和绿色回流共用同一个交通调度器，仍按容量 2、双向共享、FIFO 排队。
- 可以同时存在**一个修复任务和一个建设请求**。修复优先预留尚未支付的真实母核余额；预留仍包含在母核余额中，
  实际派送才扣款。其他用途读取扣除实际预留后的可花余额，不把未筹到的钱当成资金，也不撤销已有在途或接收预留。
  新到账营养先满足有效修复预算；这只是资金优先级，不改变交通 FIFO。
- 暂停保留生命、已付款额度、在途和缓存，不推进修复，并释放尚未支付的预算。继续时重新申请预算。
  取消退回未消费缓存和可返还在途一次、释放未用预留；**已消费的营养和已恢复生命保留**，
  未用完的已消费恢复额度随取消丢弃，因此重新请求可能产生新的向上取整费用。退款不增加累计回收。
- 目标/端点删除、母核失效或重开终止原任务，旧回调不能给新任务付款或恢复生命。正常生长中的合法端点交接
  在固定作业端不变时兼容；若交接会移动已固定作业端，则安全取消，不偷换收货位置。

## 第六阶段第四小轮：断路恢复行为

本轮把 `HyphaEdge.entry_enabled = false` 作为临时断路：仍保留同一条边、端点、货物和账目，
不包含敌人破坏、组织生命值或营养修复。五类实际货物继续共用同一个容量调度器。

### 断路时货物怎样处理

- **还在菌结**：剩余路线不可用时，从这个实际节点重新规划到原最终目标；有旁路就继续，无路则等待。
- **已在断段内**：状态为 `blocked`，保持世界位置、段进度、货物和原通行凭证；原边恢复后继续。
- **正在正常边上，后续段断开**：先走完当前段，在下一节点处理；已经走过的段断开不取消运输。
- 临时断路、等待和改道不会发中断信号，不退款、不放下尸体、不复制尸骸批次或消化产物，接收预留保持。
- 主动取消、接收对象/任务消失、调度器重开等仍按原规则唯一结算。永久删除当前所处边或端点会安全终止；
  只删除尚未进入的下一段则在节点重新找路/等待，删除最终目标始终终止。

改道调用原 `TransportRouter`，成本仍为距离/速度加预计等待，结果无环且同快照稳定。
只在剩余路线不可用时改道，容量拥堵沿原 FIFO 等待，不因等待估计的小变化每帧换路。
无路时只在拓扑、通行开关或名义容量变化后重试。如果费用估计为无穷、但静态可用路线仍存在
（例如缩容后队首大包暂时过不去），保留一条稳定可用路线继续排队，避免把估计当成永久断路。

包快照新增固定最终目标、节点/边位置类型、路线版本、重规划尝试次数与启动/终态信息。
业务在途检查改用纯查询 `is_transport_valid(target, task_id)`，到货用
`has_arrived_at(target, task_id)` 验证实际抵达；最初路线只用于派发准入，不再用于在途退款。
付款来源、原收货人、数量、货物/产物/批次身份、建设任务和胃囊预留不随路线变化。
合法的“生长尖端形成已付费菌结”通过明确的端点交接保留当前许可，供养继续前往同一生长尖端；
普通外部改端点不会被当作这种施工交接。

### 失联菌域

失联后立即退出有效采集覆盖，但保留灰色虚线残影和失联标识：先维持 **5 秒**，随后 **10 秒**内
线性收缩并变暗至消失。恢复连接时从当前显示半径继续扩张，亮度按每秒 0.5 恢复。
相同失联快照不会重置计时；节点删除立即清除残影。另一个连通节点仍覆盖的位置继续有效。
新回收请求同时要求有效连通采集节点和可用胃囊路径，不能从灰色残影新增领取；已经认领的货物不因此丢失。

`FungalField.get_source_snapshot(node)` / `get_visual_snapshot()` 区分显示半径、有效半径、亮度、失联时间
及 `grace/decaying/recovering` 状态。旧 `is_covered` 与采集节点查询仍仅表示有效覆盖。

## 第六阶段第三小轮：交通调度接入实际运输

本轮把现有实际运输包接到 **同一个 `Systems/NetworkTrafficSystem`**：战斗补给、生长供养、
器官培育供养、普通尸体/大型尸骸批次回收、消化产物回流均使用这一个容量池。
正式 `level_01.tscn` 以及继承它的 F5 大型尸骸演示，为五个业务系统绑定同一引用并开启
`traffic_required`。缺少或错配调度器时拒绝新的派送，不自动创建私有容量池，也不退回无限容量。

### 玩家可观察的交通

每条菌丝默认容量 **2，两个方向共同计数**。黄色供养包与绿色回流包占 **1**，紫色尸体包占 **2**；
绿色 10 营养产物仍只占 1。每条边保持一条 FIFO 队列，队首尸体包等空间时，后到营养包不能越过它。

HUD 右上角显示总通行占用/容量、节点等待包数，以及繁忙菌丝的单边占用/容量和排队数，
并分列等待的黄、绿、紫包数量。这里显示的是通行单位，不是营养库存。
G/B/C/L 仍控制原有建设，P/X/R 仍是暂停、取消和重开，没有新增交通调试按键。

货物先在当前节点申请本段许可，获准才进入菌丝；到达下一节点时释放当前边，再申请下一段。
需要等待时停在已经抵达的节点，不跳到下一节点或退回出发点，也不积攒等待时间造成获准后瞬移。
零长度边也必须获准并释放；尸体从地面移动到收集菌结的拾取段不占菌丝容量，抵达菌结后才申请。
生长尖端和边长继续实时变化，供养包保留原有真实移动与抵达语义。

### 等待与资源结算

**等待容量是正常在途状态，不是中断。** 排队不会发出抵达/中断信号，不能退款、提前计入库存、
释放胃囊预留或将同一份运输再派一次：

- 战斗、生长、培育的营养仍在派发时付款；等待中的包计入原在途记录，实际到达后才进入库存或建设缓存。
- 尸体及尸骸批次继续持有原领取身份和胃囊预留；排队不能再生成同一批次或复制地面尸体。
  胃囊仍有原有空位时可以派遣其他具有唯一身份的批次，不放宽库存与批量上限。
- 绿色回流继续保留原产物和尝试身份；排队时母核不入账，实际抵达后才唯一收入。
- 取消等待、移动中取消或接收者移除，先清理通行申请/凭证，再由原业务账本唯一退款、解预留或落地。
- R 先封闭旧派发、结算全部业务运输，再重置共享交通记录，最后重载关卡；旧回调不能占用新场景的边。

本轮保留出发时确定的整条路线和原有物理断路结算策略。边/节点注销、删除或端点变化仍按原规则中断；
没有途中改道、断路停留恢复或修复。临时禁行只阻止新的进入许可，已在边上的占用可继续，节点等待不退款。
现有派发继续使用原路线选择，6.2 的加权查询模块没有被误写成“包已经自动改道”。改道相关接入留给 6.4。

### 包接口与兼容边界

两类包新增 `status_changed(snapshot)` 和只读 `get_transport_snapshot()`，状态区分
`idle`、尸体专用 `pickup`、`waiting`、`moving`、`completed`、`interrupted`。
快照包含等待原因、共享调度器身份、货物类别和单位、运输身份、当前申请/凭证、节点、边、段索引与进度。
活动申请和凭证在逐段交接或终止时清除，运输身份保留用于观察。快照读取不会推进运输或修改队列。

`NutrientPacket.start_route(route, network, traffic, task_id, cargo_kind)` 接受 `supply` / `return`；
`RemainsPacket.start_route(route, network, traffic, task_id)` 固定使用 `remains`。
旧单段 `start_transport` 和原两参数 `start_route` 保留兼容。没有调度器且未要求交通的独立旧夹具
仍能使用旧接口；**正式关卡五个入口始终要求共享调度器，不能借兼容入口绕过容量限制**。
明确传入却失效/错配的调度器也不会自动退回旧模式。

## 第六阶段第二小轮：交通调度基础（模块层）

本轮完成独立的**共享容量调度器、可用路线与成本查询**。实际 `NutrientPacket`、`RemainsPacket`、
供养、回收和营养回流仍按原流程运行，**尚未接入交通申请、节点排队或通行凭证**，接入留给 6.3。
模块测试通过只代表以下调度和查询契约通过，不代表当前画面中的货物已经受容量约束或自动绕行。
F5、G/B/C/L/P/X/R 与现有 demo 操作保持原样，没有新增交通 HUD 或调度按键。

### 容量、队列与身份

`HyphaEdge.traffic_capacity` 默认 **2**，两个方向共同使用同一份容量；`entry_enabled` 默认开启。
临时禁行保留原边对象、注册关系与端点，只停止新的进入许可；已有占用可以保留，等待队列继续按原顺序保留。
本轮不增加边的生命值、损伤、修复或实际包的断路停留逻辑。

| 通行类别 | `cargo_kind` | 容量单位 |
| --- | --- | ---: |
| 黄色供养包 | `supply` | 1 |
| 绿色回流包 | `return` | 1 |
| 尸体包 | `remains` | 2 |

容量单位只由类别决定，与包内营养数量无关，**绿色 10 营养包仍占 1 单位**。
调度器不读取或修改营养余额、库存、运输付款与退款；交通记录不是资源库存。
同一条边仅有一条双向共享 FIFO 队列，队首大包等不到足够空间时，后到小包不能越过它。
取消队首后才按剩余顺序继续审批。

`NetworkTrafficSystem.request_passage(request_key, owner, task_id, edge, from_node, to_node, cargo_kind)`
返回申请快照。`request_key` 是调用方每一跳的幂等键；调度器生成含实例和代次的 `request_id`，
获准后发出非空 `token`。相同键和参数只返回原记录；相同键配不同参数会被拒绝。
申请状态为 `queued`、`granted`、`released`、`cancelled`，拒绝结果为 `rejected`。
队列逻辑位置是 `from_node`，即这一步的起点网络节点；本轮模块不会自行移动包或判定真实到达。

一个包对象 `owner` 同时最多拥有一项等待或占用。6.3 的运输接入必须在实际抵达下一节点时
先 `release(token)`，再以新的幂等键申请下一边；持有当前凭证时提前申请下一边会被拒绝，
避免把“等下一条边”变成同时持有多条边。重复释放、重复取消和陈旧凭证不会重复扣减占用。

### 查询、取消与清理

- `get_request(request_id)` / `get_lease(token)` 查询申请及有效凭证；未知或已失效的凭证返回空字典。
- `cancel_request(request_id)` 取消等待或撤销占用；`cancel_owner(owner)` 清理包对象的当前交通记录。
- `cancel_task(task_id, generation)` 清理并注销该代次的任务，阻止回调继续用同一任务身份申请；旧代次调用无效。
- `reset()` 增加代次并清空交通记录、队列和凭证；旧申请 ID、旧凭证不能影响重开后复用的申请键。
- `get_edge_snapshot(edge)` 提供边是否有效、容量、进入开关、占用、可用容量、FIFO 队列与有效凭证。
  `get_snapshot()` 提供代次、总占用、等待数、有效申请数和逐边快照。返回容器是副本。

包退出场景、节点或边注销/移除时清理关联记录；直接改端点或排队删除则在下一次 `refresh()` / 处理帧、
或新的修改操作开始前核对。改变端点不能把旧凭证转移给另一条通路。
内部状态先提交，再发 `request_changed` / `traffic_changed`；通知中重入释放、取消或重开也不能留下旧授权。
临时缩小容量不驱逐已在边上的占用，可用量最低为零；队首暂时大于新容量时继续等待扩容，不能让后包插队。
所有新查询方法均不审批、不释放、不清理队列，不通过查询隐式调度。

### 距离与等待成本

`TransportRouter` 绑定同一网络和调度器，以 `find_route(start, end, cargo_kind, speed)` 返回
`NetworkRoute` 及距离、行进秒数、预计等待秒数和总成本。它不预订路线或占用边。
只考虑仍有效、允许进入、且容量能够容纳该类别的边；没有可用路径时明确返回未找到。

**每段成本 = 长度 / 速度 + 预计等待秒数，总成本为各段之和。**
等待估计按当前占用和 FIFO 顺序模拟批次：每个批次按一个完整的 `长度 / 速度` 时间计算，
空间不足以容纳下一个排队请求时推进一个批次，再考虑后面的请求，最后估计假想候选包的进入时间。
各批次统一使用本次查询传入的速度，不读取已有在途包的实际速度或已行进距离。
例如容量 2、已有占用 1、队首先有尸体包 2 时，后到供养包 1 的估计等待为两个批次；
若每次通行需 1 秒，该边预计成本为 `1 + 2 = 3 秒`，路由模块可以选择成本 2.4 秒的旁路。

这是规划启发值，**没有读取在途进度，也不预测未来申请或释放，因此不是精确 ETA**。
选路采用非负成本的 Dijkstra，同成本按边登记顺序与首次发现顺序稳定选择；返回路线不重复节点，
零长度边和已有环路不会让查询绕圈。查询不改变任何队列、凭证、占用或资源余额。

`NetworkSystem` 新增只读的 `get_registered_edges`、`is_node_registered`、`is_edge_valid`、
`can_enter_edge` 和 `get_topology_snapshot`。`is_edge_valid` 只判断原边和端点仍有效；
`can_enter_edge` 另检查进入开关及名义容量，**实际许可仍以调度器凭证为准**。
原 `find_route` / `is_route_valid` 继续保留物理网络及原最少段数查询语义，尚不受新增交通开关控制，
确保 6.3 之前的实际运输行为不变。

新增模块用例为 `network_traffic_test.gd`、`transport_router_test.gd`、`traffic_contract_test.gd`。
本轮最终实测结果见文末验收记录；以下 6.1 及更早章节为历史说明。

## 第六阶段第一小轮：已有菌结互连

P 暂停 / 恢复当前建设，X 取消，R 重开。暂停和缺粮保留进度，在途包仍可抵达冻结缓存。
施工中供养路径断开则等待；目标节点移除会取消任务。接通后新通路是双向网络的一部分，
后续运输可以从仍连通的一端供养，已经出发的货物仍遵循原有固定路线失效规则。

### 路线与费用

预览和实际执行共同使用 `GrowthPlanner.plan(source.global_position, target.global_position, true)`。
**两端已经存在，不收端点菌结费；新中继菌结正常收费，菌丝仍按累计长度分段付费。**
最终一段直接接到所选的实际目标对象，不按坐标找替代品，不额外生成终点，也不增加“新菌结”计数。
预览不扣款，确认不预扣完整预算，全部结构营养由原 `GrowthSupplySystem` 实际运到尖端后消费。

例如原关卡的左翼 `(440, 380)` 与右翼 `(780, 400)` 相距约 341 像素，连接预计花费
**5 点菌丝 + 2 × 4 点中继 = 13 营养**，两端原有器官保持原样。完成后原有网络继续保留，形成环路。
已有直接菌丝，或已经完成过的同一对端点的连接走廊（含中继）会拒绝重复建造；
仅有其他间接路径时仍允许连接。两条菌丝在画面上相交不会自动建立交叉路口。
路线查询沿用原有最少段数搜索，新增环路不会让查询重复访问节点，也不保证每批货物都选新增边。

取消保留已付费形成的菌丝、中继和惰性残端，**已消耗的结构费用不退还**。
未消费缓存和在途按原付款来源唯一结算，退款不计为回收收入；再次建立连接属于新任务。
重开先退出放置、使连接任务失效并结算现有供养，再重载场景，旧通知不能给新场景重复记账。

### 接口与边界

`ConnectionSystem` 保存两个实际端点并转交同一 `GrowthSystem`；连接编号就是原生长任务编号，
不另建营养账本。`preview_connection` / `request_connection` 用于报价与确认，
`pause_task` / `resume_task` / `cancel_task` / `reset` 控制当前连接。
生长快照的 `task_kind` 区分 `growth` 与 `connection`，`start_node` 表示实际供养端，
`target_node` 表示指定终点；`get_completed_endpoint` 在完成事件前已返回该实际菌结。
`ConnectionInputController` 和 `ConnectionTarget` 仅选择、预览、展示状态。

本轮仍为无障碍直线，没有容量排队、断路改道、短侧枝、自动接合或修复，没有多请求或多尖端。
新增验收为 `connection_system_test.gd`、`connection_input_test.gd`、`connection_integration_test.gd`；
本轮实测结果见文末记录。以下第五阶段内容保留为历史说明。

## 第五阶段第三小轮：远处种攻击芽

自动在该任务实际形成的终点菌结上培育攻击器官。成熟后立即接入原有选择、射程、战斗和自动补给。

### 费用与结算

**总费用 = GrowthPlanner 的完整伸展费用 + 12 点器官培育费。**
规划费已包含终点菌结，不能再收一次：320 像素示例是 **16 + 12 = 28**，不是 32。
其中器官始终是 **8 点结构 + 4 点付费启动库存**，有效培育时间至少 3 秒。
标记和预览不扣款，也不提前一次扣完整预算。两个阶段分别沿用实际供养、到达、消费和退款。

HUD 和落点标记显示统一建设身份、当前阶段、等待原因、费用拆分、已投入和剩余需求。
“已投入”包含已经转入器官的启动库存；资源守恒时这 4 点只计在器官库存，不能又计为结构消耗。
“剩余需求”扣除已消费、已送达缓存和启动预留；已付款在途仍可属于待送达需求，不能据此重复派包。

## 第五阶段第二小轮：已有菌结培育攻击器官

本轮允许在**已有、成熟、连通存活母核且没有器官的菌结**上培育普通攻击器官。
F5 仍运行包含大型尸骸的演示，保留原来的六个敌人及两套预置攻击器官和一个胃囊。
预置三个菌结的槽位都已占用；可先按 **G** 从右翼 `(780, 400)` 向 `(900, 400)` 伸展，
这一段长 120、花费 6 营养。完成后左键选择新菌结，点击 **“C 培育攻击器官”** 或按 **C**。

培育总费固定 **12 营养 = 8 结构 + 4 启动库存**，不会再收菌结费。
营养以现有黄色包从母核沿网络运到宿主菌结，实际到达后才能使用。
结构分八步，每步消耗 1 点已送达营养并推进 0.375 秒，至少累计 **3 秒有效培育时间**；
缺粮、失联或暂停时保留已付款步骤和时间进度。运输和等待会延长实际完成时间。
结构和时间完成后，将另 4 点已送达的启动营养转入成熟器官，初始库存恰好为 4。

成熟前幼芽不射击、不登记为战斗补给对象；成熟后仅生成一套 `AttackOrgan` 与 `SporeWeapon`，
两者仍是宿主下的兄弟节点，武器位于 `(0, -28)`，射程 100。宿主和网络保持原样，
由关卡现有动态登记接入选择、射程、攻击及 `SupplySystem` 自动补给。
选中新器官后，N 手动补给、E 消耗库存等原操作仍有效。

### 单建设请求与取消规则

同时只允许一项建设：**伸展期间不能开始或继续培育；培育期间不能新建伸展目标**。
暂停或等待营养的任务仍占用建设请求；战斗、尸体回收、胃囊消化和绿色回流继续运行。
规则由培育创建接口和生长的 `construction_blocker` 检查，按键与按钮也显示相同限制。

- **P 暂停/恢复**当前培育或伸展。暂停培育停止新请求；已经付款的在途包继续送达并进入冻结缓存。
- **X 取消培育**停止请求、取消在途并退还未消费营养，包括尚未转入成熟库存的启动预留。
  每笔退款回到原付款母核一次，不计入累计回收；已经投入结构的营养不退款。
- 取消后幼芽留在原菌结，保留结构和有效时间进度、继续占据槽位，但释放全局建设请求。
  重新选择它并点击 **“C 继续培育”**，只补剩余费用；继续会分配新的任务身份，旧包不能投递给新任务。
- **R 重开**先结算培育供养，再清理培育状态并加载新场景。旧运输、旧任务与成熟事件不能重复生成器官、
  退款或启动库存。

HUD 根据选择显示可培育、已占用、失联、建设忙碌、营养不足及退款待结算等原因。
余额不足时仍可建立等待中的培育请求，随后由真实供养推进。一个菌结最多培育一个器官；
已有攻击器官、胃囊和保留的幼芽都视为占用。

### 培育资源与接口

`CultivationSystem` 管理任务与幼芽，不读写母核余额；`CultivationSupplySystem` 管理付款、真实运输与退款；
`CultivationInputController` 只转交选择和操作。主要查询与控制为：

- 槽位：`get_organ_occupant()`、`get_organ_bud()`、`get_organ_slot_state()`，及按唯一 ID 预留、提交、释放槽位。
- 培育：`start_cultivation(host)`、`continue_cultivation(host)`、`pause_task()`、`resume_task()`、`cancel_task()`。
- 供养：`get_delivery_target(task_id)`、`get_requested_nutrition(task_id)`、
  `receive_nutrition(task_id, shipment_id, amount)`、`take_unspent_nutrition(task_id)`。
- 审计：`get_task_snapshot(task_id = 0)`、`get_bud_snapshot(host)`、`get_resource_snapshot()`、
  `get_shipment_records()` 与 `get_supply_snapshot()`。

资源快照的 **结构已消耗、未消费缓存、启动预留**互不重叠。`startup_transferred` 只记录已转入器官的历史量，
守恒时计入器官库存，不能再额外加一次。`consumed_nutrition` 用于供养账本核销，等于结构投入加已转入库存；
继续任务以原结构投入为基线，避免把已付费部分再次扣款或冲销。取消的历史任务快照不会随新任务进度变化。

战斗储备继续使用每个活跃器官的两发缺口 `max(0, 2 × 每发消耗 - 本地库存 - 已付款在途)`。
培育只能花费母核余额扣除这部分储备后的营养，已经扣款的培育在途不再从余额重复扣除。

本轮不在远处自动延伸后建造，不实现消化器官培育、分化、移植或组织受损。
新增四组测试为 `cultivation_system_test.gd`、`cultivation_supply_test.gd`、
`cultivation_input_test.gd` 和 `cultivation_integration_test.gd`；实际验证结果见文末「第五阶段第二小轮验收」。

## 第五阶段第一小轮：大型尸骸

本轮加入一种有限资源点：默认 **80 营养，每批最多 10**。尸骸本身不进入胃囊，必须先形成独立
尸体批次，再复用现有「紫色尸体包 → 胃囊队列 → 消化产物 → 绿色营养回流 → 母核入账」流程。
普通敌人的尸体仍为 4 营养，战斗、消化和回流参数保持原值。

按 **F5** 运行新的 `scenes/levels/large_carcass_demo.tscn`。它继承原关卡，右侧世界坐标
`(1120, 440)` 放置一处大型尸骸，初始在有效菌域之外。按 **G** 后点击 `(1100, 400)` 的十字标记，
从右翼菌结向右伸展，预计花费 16 营养。至少第二个成熟菌结展开菌域后，才会开始分批采集。
源点显示剩余量和域外、无路、胃囊满、采集中、耗尽等状态；“源点耗尽”仅表示全部资源已形成批次，
余下运输、消化与回流仍会继续。**绿色包实际到达后**才增加可用余额和累计回收。

原 `level_01.tscn` 保留第四阶段的 4 营养域外尸体夹具。独立演示配置为
`carcass_demo_enabled = true`、`expansion_demo_enabled = false`；原关卡默认相反，避免新资源点
影响已有回归测试。演示仍有原来六个敌人，所以画面累计回收可能包含它们的普通尸体收入。
第一小轮没有重做地图、增加腐坏、多胃囊、敌人、器官培育或新的生长机制。第二小轮的培育接入见上文。

### 资源预留与结算边界

- `LargeCarcass` 是独立 `Node2D`，不是一具价值 80 的 `EnemyRemains`。
- `reserve_batch(request_id, requested_amount = 10)` 预留一批，实际数量取可用量、配置批量和 10 的最小值。
  没有有效菌域覆盖、可用路线或胃囊接收容量时，采集系统等待，不生成批次堆积。
- 独立 `EnemyRemains` 批次形成后，`commit_batch(request_id, batch_id)` 仅扣除一次源资源；
  批次带唯一来源、请求和批次身份，随后沿现有多段路线运输。中断只让这具批次落回地面，源点不返还资源。
  重新采集时优先处理已有地面尸体和落地批次。
- 草稿加入场景时已经被领取，暂时为零营养；最终校验后填入数量并紧接提交，提交通知前源点已扣减。
  入胃囊时也先交出批次营养再通知库存，拒收则恢复同一批次，避免同步回调短暂重复统计资源。
- 创建失败时，`release_batch(request_id)` 只释放尚未提交的预留。请求 ID、批次 ID 和运输结算去重，
  已提交的批次不能通过重复提交、释放或回调再次产出。
- `get_remaining_nutrition()` 包含已预留但未提交的资源；`get_reserved_nutrition()` 是其中被占用的部分；
  `get_available_nutrition()` 是仍可领取的量，`get_harvested_nutrition()` 是累计提交量。
  始终满足 `初始总量 = 可领取 + 预留 + 已开采`，非整批总量按实际剩余量提供尾批。

守恒检查只计各阶段实际所有者：源点剩余、独立尸体（包括运输中隐藏的原批次）、胃囊队列、
胃囊产物库存和实际已回流收入。尸体包只是批次的运输表示；绿色回流仍包含在产物库存里；
预留只代表占用，均不能再加一份营养。混合场景另计初始余额、器官库存和生长/战斗消费。

统一测试和图形操作的实际结果见文末「第五阶段第一小轮验收」。

## 第四阶段：消化回流与完整扩张演示

当前已完成「指定伸展目标 → 真实供养生长 → 新菌结展开菌域 → 采集域外尸体 → 多段运往胃囊
→ 消化产出 → 绿色营养包返回母核 → 可用余额与累计回收分别更新」的完整循环。
仍保留原来一轮六个敌人、双攻击器官和一个胃囊，没有新增敌人波次。

右侧预置一具价值 4 营养的域外尸体，世界坐标 `(1120, 420)`。按 **G** 后在其附近左键放置目标，
推荐落点 `(1100, 400)`：从右翼菌结延伸 320 像素，预计消耗 16 营养，依次形成三个新菌结。

菌丝和既有网络到达胃囊；绿色回流包实际抵达母核后才获得收入。

操作沿用 **P** 暂停/恢复生长、**X** 取消、**R** 重开。暂停生长不暂停战斗、尸体运输、消化或回流。
右下角仍可点击对应按钮；普通菌结、器官选择和 N/E/H 调试操作保持可用。

### 输出空间和资源归属

- 胃囊继续串行处理已收到的尸体，消化不再依赖母核直连。消化完成只形成带唯一 ID 的产物。
- 输出上限为 **两份、20 营养**，包括已排队/正在回流的产物，以及正在消化的一份输出空间预留。
- 消化计时开始前先预留一个槽和相应营养容量；空间满时等待，回流抵达释放空间后继续。
- 尚未产出的尸体仍计入胃囊队列。输出预留仅表示空间，不能再算一份营养；回流在途营养已包含
  在胃囊输出库存中，也不能重复计数。单份超过 20 的输入保留在队列并显示产物超限。
- 中断回流会取消原包并将同一产物放回待发状态，保持 ID 和数量，恢复连接后重新发送。
  不退款、不凭空增加产物，不在运输途中改道。

`NutritionReturnSystem` 复用 `NutrientPacket` 沿网络从胃囊所在菌结返回母核，只把回流实例设为绿色。
默认每 0.35 秒尝试发送一份产物，速度为 80 像素/秒；一份包携带该产物的全部营养。
普通黄色供养包及其结算没有改变。

### 到达事件和独立累计回收

事件契约为 `MotherCore.digestion_product_arrived(product_id: String, nutrition: int)`。
只有实际回流包到达时，运输系统才调用 `accept_digestion_product(product_id, nutrition)`；
**母核是唯一的余额入账方**，先记录 ID 再入账并发出事件，重复 ID 不会重复加钱。
初始营养、普通 `add_nutrition`、供养退款和内部转运都不触发此事件。

`ColonyProgress` 只监听该到达事件，跨来源按产物 ID 去重，维护累计回收和产物数。消费不会降低
累计回收，它也不修改母核余额。HUD 顶部是当前可用余额，左下角分别显示胃囊、输出预留、绿色
回流在途和 **累计回收**；“已消化”不再代表收入已经抵达。

主要查询：胃囊的 `get_output_products/count/nutrition/snapshot()`；回流系统的
`get_return_snapshot()`、`get_in_transit_count/nutrition()`、`get_shipment_records()`；
累计模块的 `get_total_recovered()`、`get_product_count()`。回流记录是运输尝试，胃囊记录是唯一产物库存。
重开先取消回流、清理胃囊和累计统计，再载入新场景；旧包回调无法给新场景入账。

第四阶段未包含大型尸骸和培育芽；第五阶段已实现的接入见上文。分化、主脉升级、旁路改道、
多胃囊并行和更多敌人波次仍未实现。

## 第三阶段：单尖端真实生长

已接入「放置目标 → 沿现有网络运输营养 → 尖端延伸 → 形成菌结 → 菌域展开」的实际游戏链路。
本阶段为无障碍地图、同时一个伸展目标和一个生长尖端。按 G 或点击右下角按钮进入放置模式，
鼠标预览路线、距离、新菌结位置和统一费用；左键确认，右键/Esc 退出放置。地图操作区域为
世界坐标 `Rect2(0, 230, 1200, 410)`，上下方留给现有 HUD。普通菌结和器官仍可选择。

起点选择距落点最近、与母核连通的成熟菌结或母核，同距按实例 ID 决定；临时尖端和取消残端
不能作为起点。标记和预览不登记网络、不提供菌域、不扣款。缺粮时仍能放置目标，随后等待供养。
当前任务完成或取消后可以放置下一个目标，不支持已有目标改向。

### 生长投入与节点形成

`GrowthSystem` 与预览共用关卡的 `growth_planner`，直接读取它给出的分段、节点位置和费用。
尖端默认以 **30 像素/秒** 前进；每段开工前消费该段的延伸费，到达该段终点后，另等待并消费
菌结费，才形成成熟菌结。没有已送达营养就停住，完成后不再生成节点或消费。

临时尖端是普通 `Node2D`，通过实际已长出的菌丝登记到网络，营养包的终点就是它的当前位置。
刚放置时连接为零长度；成熟后保留完成的菌丝段，并从新菌结继续下一段。成熟菌结自动接入选择、
网络和菌域快照，菌域按原有速度逐渐展开。临时尖端不提供覆盖。

- `create_target(start_node, target_position) -> int`：创建任务并返回正 ID，拒绝时返回 0。
- `pause_task()` / `resume_task()` / `cancel_task()`：控制唯一任务；`has_active_task()` 查询是否仍在进行。
- `get_task_snapshot()` / `task_changed(snapshot)`：状态、距离进度、等待原因、已消费/已送达缓存、总费和成结数。
- `task_completed(task_id)` / `task_cancelled(task_id)`：终态事件；重复完成、取消不会继续执行。
- `get_delivery_target(task_id)` / `get_requested_nutrition(task_id)`：实际尖端，以及下一笔生长投入仍缺的营养。
- `receive_nutrition(task_id, shipment_id, amount)`：只接收已经送达的唯一运输；重复或旧任务投递被拒绝。
- `take_unspent_nutrition(task_id)`：在终态交回未消费缓存，先清零再返回，重复读取为 0。

### 真实供养与战斗储备

`GrowthSupplySystem` 独占生长营养的母核扣款、在途账目和退款。默认每 0.35 秒最多派发一个
1 营养包，沿 `NetworkSystem` 查询出的多段路线送到尖端；到达后才调用生长的接收接口。
`GrowthSystem` 不修改母核余额，`GrowthInputController` 只调用规划和任务接口。

战斗储备按 `SupplySystem.get_active_organs()` 计算：

```text
每器官缺口 = max(0, 2 × 每发营养 - 本地库存 - 已扣款的器官在途营养)
战斗储备 = 所有活跃攻击器官缺口之和
生长可用 = max(0, 母核当前余额 - 战斗储备)
```

母核当前余额已经扣除了所有已派发运输，不能再减一次生长在途。原战斗供养仍由 `SupplySystem`
负责。每笔生长运输有唯一 ID，保存扣款来源、在途与结算状态；已送达缓存保留原付款来源，
消耗按接收顺序核销，未消费的退款回到原母核。`get_shipment_records()` 可查询账目。

P 或右下角按钮暂停/恢复生长。暂停保留位置和投入，停止新供养请求，已在途包继续送达并进入
冻结缓存；战斗、采集和消化继续。X 取消目标，会终止并退还在途营养，交回未消费缓存，
保留已形成的菌结和正长度菌丝。尚未付费的末端只留下无覆盖的惰性端点，不会免费补成成熟菌结。
取消退款按账目即时处理。断网时等待、原路线运输中断后退款；连接恢复后重新请求供养。

R 重开以及母核死亡时，关卡先调用生长供养 `reset()` 清理旧任务和运输，重开后的场景使用全新账目。
第三阶段限于单目标伸展；第四阶段加入的消化回流见上文。仍未实现短侧枝、绕障、目标改向、
多目标、双尖端、器官芽或分化。

## 第二阶段：多器官供养与菌域采集

当前 demo 预置母核、三个菌结、两个攻击器官和一个胃囊。右翼器官经过后方菌结接受多段供养，
两个攻击器官轮换获得补给。尸体只有在有效菌域内、存在到胃囊的路线且胃囊有容量时才会被领取。
关卡动态登记菌结、菌丝和攻击器官，动态加入的器官也支持选择与库存显示；没有加入玩家建造功能。

### 运输接口与结算

两种运输包统一使用 `start_route(route: NetworkRoute, network_system: NetworkSystem = null)`，
按每段的起终点和方向移动。尸体包保留从地面落点移动到收集节点的过程。
原有单段 `start_transport(...)` 作为兼容入口保留。

`arrived(packet)` 和 `interrupted(packet)` 是互斥的最终通知。`cancel_transport()` 归入中断，
重复取消、回调重入和节点退出不重复产生最终结果。系统以运输记录 ID 固定原始资源归属，
先删除记录再结算，运输包退出时的后备清理也不会重复入账或退款。

`NetworkSystem.is_route_valid(route)` 检查整条既定路线的节点、边登记、方向与端点。
任一原路线段失效都中断运输，包括已经走过的段；新派发重新查询路线，途中不自动改道。
注销一条仍在场景中显示的边也会使在途路线失效。

### 多器官供养接口

- `register_organ(organ)` / `unregister_organ(organ)`：幂等登记、移除；移除接收者时取消其在途供养。
- `get_registered_organs()`：有效登记器官；`get_active_organs()`：可以处理、母核存活且供养可达的器官，供生长系统计算战斗储备。
- `request_supply(organ = null)`：向指定登记器官发送 1 营养；默认使用有效的 `target_organ`，否则取首个登记器官。
- 自动调度每次最多成功发送一个包，轮换扫描低库存器官，跳过失联、停用或已足量的目标。

配置 `network_system` 后使用网络查路；旧单器官配置在未指定网络时仍可使用 `target_organ` 与 `supply_edge`。
已有网络但查不到路线时不会退回旧直连。发送时扣款，失败释放预留并退款，抵达才增加器官库存。

### 菌域采集接口

`RecyclingSystem` 接收 `fungal_field`、`network_system` 和唯一的 `digestive_organ` 引用。
`try_dispatch()` 按尸体容器顺序寻找可用尸体，再按场域候选顺序，选择仍连通母核且有胃囊路线的节点。
候选包含母核；最近候选无法通往胃囊时继续尝试其他候选。没有覆盖、路线或容量时等待。

领取时预留胃囊容量并调用尸体的唯一认领接口；到达只进入队列，中断释放预留并把原尸体放回包的最后位置。
`RecoveryOrgan` 和固定 320 半径不再参与关卡接线。第二阶段完成时消化仍检查原有 `core_edge` 并直接入账；
第四阶段已移除该消化连接限制和即时入账，改为有限输出存储和实际回流抵达结算。

## 第一阶段基础模块

本阶段增加网络查询、独立菌域和无障碍直线生长规划。关卡负责登记现有母核、菌结和菌丝，
并把连通状态作为覆盖源交给菌域。地表菌域常显，选中武器时显示琥珀色射程圈。
生长规划器挂在关卡的 `growth_planner` 属性上，可供后续预览与执行读取同一份结果。

第二阶段将网络路线接入供养和尸体运输，将菌域查询接入尸体采集；第三阶段增加独立的生长执行、
输入和生长供养模块。规划器本身仍然是纯查询，不生成对象或结算资源。

### 网络查询

`scripts/network_system.gd` 管理登记与查询，`scripts/network_route.gd` 保存一次查询的路线：

- `register_node(node, is_mother_core = false)` / `unregister_node(node)`：支持母核、菌结和普通 `Node2D` 临时尖端。
- `register_edge(edge)` / `unregister_edge(edge)`：边的两个端点须已登记；节点移除时移除关联边的登记。
- `is_connected_to_core(node)`：查询母核连通性；`find_route(start, end)`：查询任意两个已登记节点间的路线。
- `get_registered_nodes()`：返回有效节点；`network_changed`：登记变化通知。

路线包含 `found`、`start_node`、`end_node` 和 `segments`。每段包含 `edge`、通行起终点及 `forward`；
`forward = false` 表示沿原边反向走。起终点是同一个有效节点时，结果为找到路线、零段；
无法到达时为未找到、零段。BFS 选择段数最少的无环路线，尚未考虑距离、容量与等待。
查询读取当前边端点，显式移除、端点失效和对象删除都会影响后续查询。

### 独立菌域

`scripts/fungal_field.gd` 的 `set_sources(Array[Dictionary])` 接收外部快照，每个条目为：

```gdscript
{"node": node, "kind": &"core", "connected": true} # 可选 "radius" 覆盖默认半径
{"node": junction, "kind": &"junction", "connected": true}
```

模块不依赖网络系统。半径按世界坐标计算，母核默认 140、菌结 110，默认每秒展开 140 像素；
这些参数可以在关卡 `World/FungalField` 检查器调整。重复提交快照保留展开进度。
画面和 `is_covered(position)` 使用同一有效半径，`get_effective_radius(node)` 可读取展开状态。
断网立即停止有效覆盖与新采集入口，恢复后从零展开；完整缓冲和衰退留待后续阶段。

重叠区域绘成连续菌域。`get_collecting_nodes(position)` 返回去重的候选节点，
按距离、实例 ID 排序；`get_collection_node(position)` 只返回其中一个入口或 `null`，
不能把候选列表当成多个资源所有者。查询本身不认领或修改尸体，现有尸体的唯一认领仍由回收系统管理。

### 生长规划与费用

`scripts/growth_planner.gd` 提供 `plan(start_position, end_position, endpoint_exists = false)`。
返回 `valid` / `error`、起终点、距离、分段 `segments`、新增菌结 `junction_positions`，
以及延伸、菌结和总费用。每段也包含起终点、长度、累计距离及费用，后续执行直接消费这些明细。

- 已有起点免费；每 120 像素布置一个中间菌结，终点另形成菌结，恰好落在间距倍数上时只计一次。
- 每个新增菌结 4 营养；`endpoint_exists = true` 时不创建或收费终点菌结。
- 延伸费用是整条路线的 `ceil(总距离 / 80)`。每段分配前后累计费用之差，不对各段独立向上取整。
- 零距离没有分段、新菌结或费用。无效参数返回失败结果，不产生游戏状态变化。

| 距离 | 新菌结数 | 延伸费用 | 总费用 |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 80 | 1 | 1 | 5 |
| 80.01 | 1 | 2 | 6 |
| 120 | 1 | 2 | 6 |
| 120.01 | 2 | 2 | 10 |
| 240 | 2 | 3 | 11 |
| 240，终点已存在 | 1 | 3 | 7 |

规划器只计算主枝直线，不处理障碍、短侧枝、目标输入或生长推进。
为处理浮点表示误差，正整数单位边界最多吸附 0.00001 像素（且不超过单位长度的百万分之一）。
一次规划最多 100000 段；费用溢出、非有限值或世界坐标精度不足以区分相邻菌结时返回失败。

## 现有资源循环 demo

一个母核、左右前线和后方三个菌结、四条连接，以及两个攻击器官和一个消化器官，
验证「杀敌 → 回收 → 消化 → 供养」的完整资源循环。
运行后 3 秒开始一轮六个敌人的防守，敌人从两个出生点交替进入，每隔 3 秒出现一个。
器官自动射击，低库存时自动补给；本轮全部击败后显示防守成功。
母核被摧毁时停止战斗与自动供养，按 R 可以重开。
防守成功后回收与消化继续运行，尾批尸体需要再等几秒才能全部转化为营养。

| 操作 | 效果 |
| --- | --- |
| 左键点击菌结或器官 | 选择所属菌结，显示武器射程 |
| 右键或 Esc | 取消选择 |
| G / 右下角伸展按钮 | 进入伸展放置；左键确认，右键/Esc 只退出放置 |
| P / 暂停按钮 | 暂停或恢复当前生长，保留进度；战斗和回收继续 |
| X / 取消按钮 | 取消生长，保留已形成网络并退还未消费营养 |
| N | 向所选攻击器官发送 1 点营养；未选择时默认左翼 |
| E | 所选攻击器官消耗 1 点营养；未选择时默认左翼 |
| H | 母核受到 30 点测试伤害 |
| R | 重新开始当前关卡 |

母核初始营养为 72；每个攻击器官初始库存为 4，容量为 6。顶部另显示所有器官的总库存与在途供养。
取消运输会释放器官预留，并将营养退回原母核；同一笔运输只结算一次。
库存加在途供养低于 3 时，调度器每隔 0.35 秒轮换尝试补给 1 点。
手动补给可以补满容量。发送时扣除母核余额，到达时才加入器官库存。
供养通过 NetworkSystem 查询通往器官所属菌结的路线，支持多段和反向通行。

## 回收与消化

敌人死亡后在落点留下尸体，默认每具含 4 点营养。回收系统每隔 0.6 秒
尝试领取有效菌域内的一具未领取尸体，收集节点需要有通往胃囊的网络路线，后方必须有空余容量。
回收包先把尸体移动到收集节点，再沿查询出的有向多段路线运输。
金色小点代表营养供养，紫色包代表尸体回收，绿色包代表消化产物回流。

消化器官容量为 4 具，排队中的尸体和在途预留共同占用容量。
到达只加入待消化队列，每具消化 1.5 秒后形成待回流产物；绿色营养包实际抵达母核才入账。
与母核失联时仍可消化已经收到的尸体，但输出槽和营养容量必须已预留；输出满后等待。
回收运输中断则释放预留，将尸体放回包最后到达的位置，线路接通后可以再领取。

六个敌人全部回收可收入 24 点营养，默认十二发射击消耗 12 点，获得用于后续成长的净收益。
两个预置攻击器官的射程设为 100，便于把击杀落点留在半径 110 的菌域内。
菌域外的尸体等待覆盖；新生长的成熟菌结展开菌域后，原采集系统便可使用新的覆盖。

## 工程约定

- 初始关卡、界面、外观和计时器放在场景中，运行时通过 PackedScene 实例化运输包、敌人、弹丸和尸体。
- 库存与武器分开；二者在同一菌结下，通过检查器引用关联。
- 参数优先通过导出属性在检查器中修改；不要在多个脚本里重复维护同一余额。
- 模型通过信号通知界面，界面只负责显示。
- 母核、菌结和敌人以落地点作为原点，用 Y 排序保持斜俯视遮挡关系；武器发射点使用局部偏移表现高度。
- 按键在 Project Settings → Input Map 中定义，测试按键暂时保留。
- GDScript 使用制表符缩进、明确类型和短函数；注释说明职责和容易误解的规则。
